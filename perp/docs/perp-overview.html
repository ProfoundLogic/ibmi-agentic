PERP: the PreSales ERP
Progress so far

We now have a working, journaled, multi-company ERP on IBM i that runs the purchasing flow from requisition to receipt, loaded with a realistic demo company. We built it so pre-sales can demo real business flows instead of isolated screens. You can sign on and use it today.

Why we’re building PERP

The ERP is how we deliver the demo. What we’re really showing is what Profound Logic tooling does to a believable IBM i business application.

A real business flow for demos

Pre-sales needed an end-to-end application that resonates across verticals: distribution, manufacturing, retail, F&B, healthcare, financial services and public sector. A single CRUD screen doesn’t do that.

An authentic “before”

Every function starts as a proper 5250 green-screen program. That gives us a genuine baseline to modernise live with Profound UI Rich Display and Genie/EJS, all over the same RPG and DB2 tables.

A CoderFlow showcase

Every step in the flow is a place for automation: auto-approval scoring, lot reconciliation, PO generation. CoderFlow agents delivered the module itself ticket by ticket, so the build history is part of the demo too.

Four demo storylines the data model was designed for

3D warehouse walkthrough

Every bin is real inventory. Click a bin to see the item and its balances. Low stock glows red. The data and coordinate service are ready; the 3D UI is still to come.

Pricing history graph

Effective-dated prices for each item and vendor, with past and announced increases, expired quotes, and preferred vendors that aren’t the cheapest.

Lot reconciliation

On some items the lots add up to less than on-hand, on others to more. CoderFlow finds the drift, repairs it and writes the audit trail.

Auto-approval

CoderFlow scores each requisition. At 85% confidence or more and $500 or less, it’s approved automatically with a full audit trail. Anything else goes to a human approver.

Try it yourself on idev

PERP runs in the PERPDEMO library on the idev partition. It takes about two minutes to get from sign-on to a live ERP screen.

  1. Connect to idev

    Open a 5250 session to idev.profoundlogic.com with IBM i Access Client Solutions or any TN5250 emulator. You can also use Genie in a browser at http://idev.profoundlogic.com:8098/profoundui/genie.

  2. Sign on with your own idev user profile

    You need a profile with a command line (===>). The shared AIDEMO agent profile signs on to a menu without one, so use your own profile.

  3. Add the PERP library to your library list

    ADDLIBLE PERPDEMO You should see “Library PERPDEMO added to library list.” The menus are library-qualified, but the programs behind them aren’t. Without this step the menus display, but every option fails because the program can’t be found.

  4. Go to the PERP main menu

    GO PERPMNU

  5. Pick a company first (option 1)

    Type 1 next to ACM – ACME Distribution and press Enter. The choice is saved in your job’s *LDA. Every PERP program reads it, and without it you’ll get “No company selected – run Select Company (PERPSELR) first.” Repeat this each time you sign on.

  6. Explore

    Start with 3 → 4 Work with Items, 7 → 4 Browse POs and 8 → 2 Reconciliation log. F3 exits and F12 goes back.
PERPDEMO is shared, live demo data. Pre-sales demos run on ACME. To try adds, changes or deletes, press F6=Add on the Select Company screen to create your own company and work in that. Don’t run the Diagnostics / Smoke Tests menu (option 5) against ACM. Those programs change data: lot reconciliation repairs the lot mismatches that were planted on purpose for the reconciliation demo and the portal reports.
Shortcut: every PERP program also has a direct launcher named PL plus the program name, for example CALL PERPDEMO/PLWRKITMR for Work with Items. It adds PERPDEMO to your library list, sets the company to ACM and opens the screen, skipping the menus and Select Company. They were built as menu options for the CoderFlow for Business Portal and always use ACM.

Taking a copy for your own work

There are three ways to work with PERP, from lightest to heaviest. One thing affects all of them: the programs refer to PERPDEMO by name in about 215 places across nearly 60 sources (SQL like perpdemo.item, menus like go perpdemo/perpinvm, the journal CLs and the PL launchers).

Demos & exploring

AUse it in place

Sign on to idev, run ADDLIBLE PERPDEMO, then GO PERPMNU. Create your own company code so your changes don’t touch ACME.

  • No setup at all
  • Shared with pre-sales, so be a good neighbour
Customer / partner IBM i

BSave & restore the library

SAVLIB LIB(PERPDEMO) to a save file, move it, then RSTLIB on the other system. You get code, objects, ACME data and the journal together.

  • Keep the library name PERPDEMO so the hard-coded references still resolve
  • The objects are compiled for V7R4M0, so the target system must be on 7.4 or later
  • The quickest way to get a full working copy, data included
Developing & extending

CBuild from source

Clone ProfoundLogic/ibmi-agentic, check out branch PERPDEMO and work in perp/. Build with codermake (or a CoderFlow task). Read perp/AGENTS.md and the Delivery Playbook first.

  • Create the journal first: build and CALL PERPJRN
  • Delete the committed stamps in perp/build/ first, or codermake will assume everything is already built
  • Load the ACME data with perp/tools/acme_seed. The generator writes qddlsrc/seed/030_acme_demo_data.sql and load.sh runs it. A load replaces every ACM row
Watch out: CPYLIB PERPDEMO MYLIB on idev does not give you an isolated copy. The copied programs still read and write PERPDEMO’s tables, and the menus still jump to PERPDEMO menus. A copy under a different library name only works after the perpdemo. qualifiers are taken out of the source.
Known limitations, tracked for fixing. These copy caveats are on the backlog: hard-coded PERPDEMO library names (PERP-103) and committed build stamps (PERP-104). Once they’re done, options B and C become a clean, any-library copy.

How it’s engineered, and what we learned

PERP is new code, and it sets conventions on purpose. Most of the lessons below are bugs that compiled cleanly and only showed up at runtime. They’re now written into the standards so nobody has to find them again.

Conventions

  • SQL DDL, not DDS: one .table.sql per table, explicit FOR SYSTEM NAME / FOR COLUMN
  • Integrity in the database: FKs and CHECK constraints declared in DDL, not in app code
  • Multi-company: company_code leads every business key
  • Journaled from day one to PERPJRN, with real commitment control (no COMMIT=*NONE)
  • Free-form RPG only, with service programs for shared logic (DOCSEQ, ITMVPRCQ, WHCOORD, REQAUTO, LOTRECON)
  • Standard audit block on every table (created/updated at/by, is_active)

Gotchas that compile cleanly

  • ctl-opt datfmt(*iso) is required. The job date format is *MDY, so dates outside 1940–2039 crash with RNQ0114
  • return; inside a begsr ends the whole program. Use leavesr;
  • Every WRITE/EXFMT format needs OVERLAY, or the subfile and messages are wiped before they display
  • Adjacent DDS fields can collide on the attribute byte (CPD7866), which silently drops column headings
  • A stale object earlier in the library list can shadow a fixed one. If a rebuild changes nothing, check DSPLIBL
